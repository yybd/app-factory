## Distribution builds

`<App>` ships through **two channels from one codebase**, as **two Xcode targets**
that share the same synced source folder. The channels diverge only in sandboxing,
which frameworks are linked, and any `#if DIRECT` code paths.

Two targets (not just build configs) are required because Sparkle is a **linked
framework**, and linking is per-target — the only way to keep the App Store binary
Sparkle-free (App Review Guideline 2.4.5).

|                  | App Store target            | Direct target                          |
|------------------|-----------------------------|----------------------------------------|
| Target           | `<AppStoreTarget>`          | `<App> Direct`                         |
| Scheme           | `<AppStoreScheme>`          | `<App> (Direct)`                       |
| Compile flag     | —                           | `DIRECT`                                |
| App Sandbox      | **On** (required by MAS)    | **Off** (not required for direct)      |
| Hardened Runtime | On                          | On (required for notarization)         |
| Auto-update      | — (the Mac App Store)       | **Sparkle** (`SparkleUpdater.swift`)   |
| Distribution     | Upload to App Store Connect | Developer ID + notarization, hosted DMG|

Both targets compile every source file (the folder is synced to both); `#if DIRECT`
alone decides what each binary contains.

```sh
xcodebuild -scheme '<AppStoreScheme>' -configuration Release build   # App Store
xcodebuild -scheme '<App> (Direct)'   -configuration Release build   # Direct
```

> ⚠️ The App Store build must contain no self-update mechanism (Guideline 2.4.5):
> Sparkle is linked only to the Direct target, so the App Store binary embeds none
> (verify: its `.app` has no `Frameworks/Sparkle.framework`).

### Sparkle auto-updates (direct build)

- `SUFeedURL` = `<appcast URL>` and `SUPublicEDKey` (Info.plist on the Direct
  target). The **private EdDSA key is in the login Keychain** under account
  `<App>` — **back it up**; losing it breaks all future updates.
- A `Check for Updates…` menu item is added; Sparkle also checks in the background
  and verifies each download's signature before installing.

**Cut a release:**
1. Bump the version; archive `<App> (Direct)` → Developer ID export → notarize +
   staple the DMG; place it in `release/`.
2. `DOWNLOAD_URL_PREFIX='<releases URL>/' SPARKLE_KEYCHAIN_ACCOUNT='<App>' ./make_appcast.sh release`
3. Upload `release/*.dmg` + `appcast.xml`, serving the appcast at the `SUFeedURL`.

The Direct target + scheme are generated by `add_direct_target.rb` (idempotent;
re-run with `SPARKLE_PUBKEY=…` if the project is regenerated).
